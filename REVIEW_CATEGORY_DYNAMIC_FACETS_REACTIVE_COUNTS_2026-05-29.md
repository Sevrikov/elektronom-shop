## Findings

### P1. Реактивные counts считаются только по первым 2000 товарам категории

Файл: `src/queries/categories.ts`  
Место: `getCategoryProductsForFacets()`, строки около 147-164.

Сейчас фасетная модель грузит товары категории через:

```ts
take: 2000
```

и дальше считает brands, attributes, price buckets в памяти. Для маленькой тестовой базы это работает. Для реального каталога это даст ложные counts, ложные disabled-состояния и ложную гистограмму, если в категории больше 2000 товаров.

Дополнительный риск: в запросе нет `orderBy`, поэтому “первые 2000” не являются стабильной бизнес-выборкой.

Почему это важно: задача была именно убрать ложное понимание у пользователя. Если пользователь двигает цену, фильтры должны показывать честные доступные варианты. При лимите 2000 проблема просто переедет на большие категории.

Как исправить:

1. Для production-режима считать counts через SQL/Prisma aggregation по всей категории, а не по срезу 2000.
2. Для каждого facet group использовать правило: учитывать все активные фильтры, кроме текущей группы.
3. Для price buckets считать распределение отдельным агрегирующим запросом по всей выборке после остальных фильтров.
4. Если временно оставляется in-memory MVP, обязательно добавить `orderBy: { id: 'asc' }` и явно пометить это как временное ограничение, но для приемки лучше не оставлять.

### P1. Кэш фасетов может не инвалидироваться после изменения товаров

Файл: `src/queries/categories.ts`  
Место: `cacheTag(\`category-products-facets-${slug}\`)`, строка около 150.  
Связанный файл: `src/actions/admin.ts`, product mutations вызывают `revalidateTag('products', 'max')`.

Новый кеш для фасетов помечен только категорным тегом:

```ts
cacheTag(`category-products-facets-${slug}`)
```

При этом админские операции с товарами, судя по текущему коду, ревалидируют в основном:

```ts
revalidateTag('products', 'max')
```

Итог: после изменения цены, бренда, stock, attributes, активности товара или удаления товара фасеты категории могут остаться старыми до истечения cache life.

Как исправить:

1. Добавить в `getCategoryProductsForFacets()` общий тег:

```ts
cacheTag('products')
```

2. Либо при product mutations дополнительно ревалидировать конкретные `category-products-facets-${slug}` для старой и новой категории товара.
3. При переносе товара между категориями ревалидировать обе категории.

Минимальный безопасный вариант: добавить `cacheTag('products')` в facet query, чтобы существующий `revalidateTag('products', 'max')` сбрасывал и фасеты.

### P1. В `PriceRangeFilter` остались inline styles, хотя правила проекта запрещают `style={{}}`

Файл: `src/components/catalog/price-range-filter.tsx`  
Места: строки около 83, 129, 147, 163.

Остались динамические inline styles:

- высота bar-сегмента гистограммы;
- left/right активной линии range;
- z-index ползунков.

Это прямо противоречит `AGENTS.md`: Tailwind CSS v4, no inline styles.

Как исправить:

1. Для гистограммы использовать квантованные CSS-классы высоты: например `h-[15%]`, `h-[25%]`, `h-[40%]`, `h-[60%]`, `h-[80%]`, `h-full`, выбранные через map.
2. Для подсветки выбранного диапазона можно не рисовать отдельный active track через left/right, а подсвечивать сами bucket-сегменты, которые попали в диапазон.
3. Для z-index использовать условные классы: `z-[3]`, `z-[4]`, `z-[5]`.
4. Если нужен сложный кастомный slider, вынести стили в `globals.css` и управлять состоянием через классы/data-атрибуты, а не через React inline style.

### P2. `PriceRangeFilter` вызывает setState во время render

Файл: `src/components/catalog/price-range-filter.tsx`  
Места: строки около 18-28.

Сейчас компонент хранит `prevProps` в state и при несовпадении props вызывает:

```ts
setPrevProps(...)
setLocalMin(...)
setLocalMax(...)
```

не внутри эффекта, а во время render. Это хрупкий паттерн для React/Next и может давать лишние рендеры или странные состояния при быстрых URL-переходах.

Как исправить:

1. Использовать `useEffect` для синхронизации локального состояния с `currentMin/currentMax/min/max`.
2. Либо сделать компонент полностью controlled: состояние цены хранится выше, а `PriceRangeFilter` только отображает и вызывает `onChange`.

### P2. `availableMin/availableMax` рассчитываются, но не используются в UI

Файл: `src/queries/categories.ts`  
Файл: `src/app/[locale]/(shop)/catalog/[slug]/page.tsx`

Backend уже считает:

- `absoluteMin`
- `absoluteMax`
- `availableMin`
- `availableMax`

Но в `page.tsx` в `priceRange` передаются только абсолютные границы:

```ts
min: facets.price.absoluteMin
max: facets.price.absoluteMax
```

Это не блокер, потому что гистограмма уже показывает доступность. Но UX можно усилить: серой/слабой зоной показать диапазон, где товаров после остальных фильтров нет, и активной зоной показать `availableMin/availableMax`.

Как исправить:

1. Передавать в `PriceRangeFilter` `availableMin` и `availableMax`.
2. Использовать их как подсказку/микро-индикатор доступного ценового коридора.
3. Не обрезать насильно slider до available range: пользователь должен видеть весь диапазон категории, но понимать, где товары реально существуют.

### P2. Атрибуты фасетов учитывают только строковые значения

Файл: `src/queries/categories.ts`  
Место: сбор `allAttributesMap`.

Сейчас в фасеты попадают только:

```ts
if (typeof val === "string")
```

Если позже в `attributes` появятся числовые значения, boolean или массивы, фасеты их проигнорируют. Для текущего seed это может быть нормально, но для реального каталога электротоваров часто нужны числовые технические параметры: ток, напряжение, мощность, полюса, IP, емкость, длина, сечение.

Как исправить:

1. Добавить нормализацию `string | number | boolean | string[]`.
2. Для числовых параметров сделать отдельный тип facet: `numeric-range` или `numeric-buckets`.
3. Для массивов считать каждое значение отдельно.

## Что реализовано хорошо

1. Главное направление правильное: counts считаются с учетом всех остальных фильтров, кроме текущей группы.
2. Нулевые варианты переводятся в disabled-состояние.
3. Выбранные варианты с 0 товаров остаются видимыми, чтобы пользователь мог их снять.
4. Brand logo/fallback в фильтрах сделан по смыслу правильно.
5. Product query и product grid продолжают жить отдельно, то есть карточки не переписаны заново.
6. TypeScript, lint и build проходят.

## Приемочные сценарии после исправления

1. Открыть категорию с несколькими брендами и ценовыми диапазонами.
2. Выбрать узкий диапазон цены, в котором остаются товары только одного бренда.
3. Проверить, что остальные бренды отображаются disabled и не кликаются.
4. Снять цену и проверить, что бренды снова активны.
5. Выбрать бренд, затем технический атрибут, затем диапазон цены.
6. Проверить, что все остальные фильтры пересчитались относительно текущего состояния.
7. Проверить, что выбранный фильтр с 0 товаров не исчезает и его можно снять.
8. Проверить, что price histogram показывает пиксельные полоски только там, где есть товары после остальных фильтров.
9. В админке изменить цену/бренд/stock товара, вернуться в категорию и убедиться, что counts обновились после revalidate.
10. Проверить mobile drawer: disabled-состояния, counts, сброс фильтров, отсутствие перекрытий.

## Решение по приемке

Не принимать как полностью закрыто.

Можно считать закрытыми:

- базовый UI фильтров;
- URL-driven state;
- микро-логотипы брендов;
- первичный MVP гистограммы;
- компиляционную корректность.

Нужно доработать перед финальной приемкой:

- убрать лимитную in-memory модель как источник истины для counts или заменить ее агрегирующей моделью;
- исправить cache invalidation фасетов;
- убрать inline styles из `PriceRangeFilter`;
- убрать setState во время render;
- при возможности вывести `availableMin/availableMax` в UX как дополнительную подсказку.
