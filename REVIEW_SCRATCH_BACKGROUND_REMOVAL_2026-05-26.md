# Review: scratch/background removal prototype

Дата: 2026-05-26  
Папка: `C:\Users\sevri\Сайт\elektronom\scratch`  
Цель ревью: проверить мини-проект очистки товарных изображений от фона перед использованием в рабочем контуре сайта.

## Краткий вывод

В `scratch` собран полезный исследовательский прототип: есть адаптивная маска, per-image конфиги, обработка внутренних отверстий, visual comparison sheets и ручная настройка сложных кейсов. По канистрам результат уже близок к применимому для каталога.

Но сейчас это не production-инструмент, а лаборатория с несколькими версиями алгоритма. Главные проблемы: проект не запускается воспроизводимо в текущем окружении, PNG сохраняется под исходными JPG-именами, конфиг парсится из TypeScript регулярками, а логика продублирована в нескольких скриптах и уже содержит расходящиеся баги.

## Findings

### P1. Инструмент не воспроизводится из стандартной команды

Факты:

- В `scratch` нет `README`, `requirements.txt`, `pyproject.toml` или другого описания Python-зависимостей.
- Команда `python scratch\run_removal.py` в текущем окружении не запускается: `python` не найден.
- Команда `py -3 scratch\run_removal.py` тоже не дала рабочий запуск: Windows launcher пытается открыть недоступный Python.
- Скрипты требуют минимум `Pillow` и `numpy`, но это нигде не закреплено.

Риск: разработчик или CI не смогут повторить результат. Будет ситуация “у меня на ПК работало”, а на другом компьютере или сервере нет.

Как исправить:

1. Вынести инструмент из `scratch` в нормальную папку, например `tools/image-bg-removal/`.
2. Добавить `requirements.txt`:

```txt
Pillow==10.4.0
numpy==2.0.2
```

3. Добавить `README.md` с одной основной командой:

```powershell
py -3.11 tools\image-bg-removal\remove_bg.py --input public\images\products --output delivery\bg-removed --config tools\image-bg-removal\config.json --compare
```

4. Добавить проверку окружения в сам CLI: понятная ошибка, если `Pillow`/`numpy` не установлены.

### P1. PNG сохраняется с исходным расширением JPG

Файлы:

- `scratch/run_removal.py:64-65`
- `scratch/run_removal.py:106-108`
- `scratch/run_removal.py:355-357`
- `scratch/run_removal.py:376-377`

Проблема: скрипт вызывает `img.save(..., "PNG")`, но путь строит через исходный `filename`. Если входной файл `*.jpg`, на выходе получится PNG-байты в файле с расширением `.jpg`.

Риск:

- CDN, Next Image, браузер, Cloudinary или импорт в админку могут определить неверный MIME.
- Разработчик визуально увидит файл, но дальше пайплайн может ломаться нестабильно.
- Файлы сравнения вида `comp_*.jpg` тоже фактически PNG.

Как исправить:

```python
stem = os.path.splitext(filename)[0]
out_path = os.path.join(output_dir, f"{stem}.png")
comp_path = os.path.join(output_dir, f"comp_{stem}.png")
```

Для `skipProcessing` тоже не сохранять PNG под `.jpg`. Если файл пропускается без изменения, либо копировать оригинал как есть, либо явно писать `stem.png` после конвертации.

### P1. Конфиг парсится из TypeScript регулярками

Файл: `scratch/run_removal.py:7-57`  
Источник конфига: `src/config/image-arbitration.ts:10-103`

Проблема: Python-скрипт читает `src/config/image-arbitration.ts` и регулярками вытаскивает `IMAGE_ARBITRATION_CONFIGS`. Это хрупко:

- изменение форматирования TS может сломать парсинг;
- комментарии, trailing commas и вложенные поля могут вести себя неожиданно;
- при неудаче скрипт просто вернет `{}` и ничего нормально не обработает.

Как исправить:

1. Сделать единый машинно-читаемый конфиг `tools/image-bg-removal/config.json`.
2. Если этот конфиг нужен фронту, генерировать TS из JSON или импортировать JSON в TS.
3. Добавить валидацию конфига: неизвестные поля, пропущенные файлы, отрицательные значения, отсутствующие исходники.

### P1. В нескольких версиях алгоритма уже есть расходящиеся ошибки

Файлы:

- `scratch/test_ultimate_arbitrator.py:193-204`
- `scratch/test_adaptive_outlines.py:228-235`

Проблемы:

1. В `test_ultimate_arbitrator.py` есть реальный координатный баг:

```python
nx, ny = x + dx, cy + dy
```

Тут используется старый `cy`, а должен быть `y`. Это может искажать topological margin expansion.

2. В `test_adaptive_outlines.py` есть мертвая строка:

```python
nx, ny = x + dy, y + dy
nx, ny = x + dx, y + dy
```

Первая строка сразу перезаписывается. Это не ломает текущий результат, но показывает, что версии копировались вручную и расходятся.

Риск: разработчик может взять не тот файл как “последний правильный”. Ошибки будут возвращаться при следующих экспериментах.

Как исправить:

- Оставить один канонический модуль алгоритма.
- Все `test_*` превратить в тесты/fixtures, а не альтернативные реализации.
- Запретить копипасту алгоритма между файлами.

### P1. Нет автоматических acceptance-тестов качества маски

Сейчас качество проверяется через PNG comparison sheets глазами. Это полезно, но недостаточно.

Нужно добавить golden cases:

- темная канистра на светлом фоне;
- светлая/серая канистра;
- товар с внутренними отверстиями;
- товар с белыми элементами, которые нельзя удалить;
- товар с тенью/отражением снизу;
- lifestyle/spec изображения, где `skipProcessing: true`.

Минимальные метрики:

- выход всегда `.png` с alpha-каналом;
- фон в углах имеет `alpha = 0`;
- bbox товара не обрезан;
- доля прозрачности в ожидаемом диапазоне;
- внутренние отверстия удаляются только для нужных классов;
- на темном и светлом фоне нет грубого ореола.

### P2. Алгоритм тяжелый по памяти и времени

Файлы:

- `scratch/run_removal.py:113-135`
- `scratch/run_removal.py:210-235`
- `scratch/run_removal.py:281-318`

Проблема: для изображения используются `set` и `dict` с ключами `(x, y)` на пиксельном уровне. Для 1000+ px изображений это сильно дороже, чем `numpy` boolean/int masks.

Риск: при массовой обработке каталога скрипт будет медленным, нестабильным и прожорливым по памяти.

Как исправить:

- `visited_coarse` заменить на `np.zeros((height, width), dtype=np.bool_)`.
- `visited` заменить на `np.zeros((height, width), dtype=np.uint8)`.
- Flood-fill оставить очередью, но статусы хранить в массиве.
- Добавить лог времени обработки и лимит размера входного изображения.

### P2. Деструктивная обработка края может съесть светлые детали товара

Файл: `scratch/run_removal.py:320-353`

Проблема: feathering/fringe cleanup снижает alpha для светлых пикселей рядом с фоном. Это может быть нормально для белого ореола, но опасно для:

- белых наклеек;
- серых корпусов;
- белых проводов;
- бликов на пластике;
- текстовых маркировок возле края.

Как исправить:

- Добавить тесты на белые/серые товары и товары с мелким текстом.
- Разделить “удалить фон” и “смягчить край” на разные параметры конфига.
- Для edge cleanup использовать расстояние до маски и локальный контраст, а не только `min_chan > 150`.

### P2. `scratch` смешивает исходники, результаты, отладку и старые версии

Факты:

- В папке лежат исходные изображения, comparison sheets, временные PNG, JS-скрипты, HTML-дампы, анализаторы, отладочные trace-файлы и несколько реализаций одного алгоритма.
- Есть большие временные изображения и zero-byte файл `live-product.html`.

Риск: трудно понять, что является источником правды, что можно удалить, а что нужно сайту.

Как исправить:

Рекомендуемая структура:

```txt
tools/image-bg-removal/
  README.md
  requirements.txt
  remove_bg.py
  config.json
  tests/
    fixtures/
    test_remove_bg.py

delivery/bg-removal/
  comparisons/
  output/
  REVIEW_*.md

scratch/
  только временные эксперименты, не ссылка из документации
```
