## Что подтверждено

### 1. Unit-тесты NormGuard и validation появились

Файл:

- `scripts/test-engineering.ts`

Проверяются ключевые правила:

- отрицательная мощность потребителя блокируется;
- длина трассы более 300 м блокируется;
- валидная нагрузка проходит;
- 3-фазная нагрузка при 230 В блокируется;
- 3-фазная нагрузка при 400 В проходит;
- влажная зона без дифференциальной защиты получает `danger`;
- наличие резервного источника требует проверки заземления/нейтрали и получает `danger`;
- наличие `danger` приводит к блокировке оформления/заказа.

Это закрывает главный пробел предыдущего ревью: раньше NormGuard был логикой без минимального автоматического safety-контроля.

### 2. Engineering AI prompt вынесен из UI

Файл:

- `src/lib/assistant/prompts/engineering.ts`

Плюсы:

- генерация инженерного prompt больше не размазана по `assistant-panel.tsx`;
- добавлена `EngineeringDraftSchema`;
- перед отправкой AI черновик проходит `.safeParse()`;
- `assistant-panel.tsx` стал тоньше и безопаснее.

Это правильное направление для будущей RAG/agentic-архитектуры: UI не должен сам собирать критичные инженерные инструкции.

### 3. Системное правило для AI добавлено

Файл:

- `src/lib/assistant/prompts.ts`

Добавлено правило, что AI не должен переопределять, отменять или оспаривать решения NormGuard. Помощник должен объяснять причины блокировки и предлагать безопасный путь исправления.

Это важно: инженерный AI здесь должен быть консультантом и интерпретатором, а не авторитетом выше safety-движка.

### 4. `defaultValue` в переводах AI panel удалены

Проверка по `src/components/engineering/engineering-workspace.tsx` не нашла `defaultValue` в вызовах `t(...)`.

Это снижает риск того, что UI будет тихо показывать неучтенные строки вместо управляемой локализации.

## Остаточные замечания

### P1. Проверить runtime labels единиц измерения в `calculators.ts`

Файл:

- `src/lib/engineering/calculators.ts`

При чтении файла в PowerShell в runtime-labels видны признаки mojibake для единиц:

- `РјРјВІ` вместо `мм²`;
- `РјРђ` вместо `мА`.

Даже если часть проблемы связана с отображением консоли, для core-логики лучше не хранить такие единицы в кириллице.

Рекомендация:

- заменить runtime labels на ASCII-safe формат: `mm2`, `mA`, `A`, `kW`, `V`;
- человекочитаемую локализацию единиц выполнять в UI/i18n-слое;
- не смешивать расчетное ядро и локализованный текст.

### P2. В `engineering-workspace.tsx` остались точечные hardcoded-строки

Файл:

- `src/components/engineering/engineering-workspace.tsx`

Найдены строки, которые стоит вынести в i18n:

- `резерв` в строке summary входного автомата/резерва;
- условная строка ошибки формы: `Будь ласка, виправте помилки:` / `Пожалуйста, исправьте ошибки:`.

Это не блокирует Sprint 1, но лучше закрыть перед Sprint 2, чтобы не копить локализационный долг.

### P2. Prompt templates пока hardcoded в TypeScript

Файл:

- `src/lib/assistant/prompts/engineering.ts`

Для Sprint 1 это приемлемо, потому что prompt теперь хотя бы изолирован в специализированном модуле.

Для следующего уровня лучше:

- хранить prompt templates как отдельные версионируемые файлы;
- добавить `promptVersion`;
- логировать версию prompt вместе с ответами AI;
- отделить user-facing i18n от system/developer prompt-templates.

### P3. Unicode comments в `calculators.ts`

В `roleWords` runtime-ключи переведены на Unicode escape-последовательности, но рядом остались кириллические комментарии.

Это не влияет на выполнение кода, но если цель — полностью убрать риск кодировочных артефактов из core-файла, комментарии лучше:

- удалить;
- или заменить на ASCII transliteration.

### P3. Unit-тесты пока script-based

Команда:

```powershell
npm run test:engineering
```

Работает и закрывает MVP-задачу.

На следующем этапе лучше перенести проверки в стандартный test runner, чтобы получить:

- нормальную группировку кейсов;
- exit codes и stack traces по каждому тесту;
- возможность запускать subset тестов;
- интеграцию в CI как отдельный job.
