# ТЗ: AI-помощник технического подбора товаров для Elektronom

Дата: 2026-05-25  
Проект: Elektronom  
Цель: разработать AI-помощника, который помогает покупателю подобрать товар из каталога, отвечает как технический консультант, опирается на документацию, остатки, характеристики товаров и при необходимости сверяет наличие на сайте/в каталоге поставщика.

## 1. Концепция

AI-помощник должен быть не обычным chatbot, а техническим консультантом по каталогу Elektronom.

Он должен уметь:

- понять задачу покупателя обычным языком;
- задать уточняющие вопросы;
- подобрать подходящие товары из каталога;
- объяснить, почему выбран именно этот товар;
- свериться с технической документацией;
- учитывать остатки и доступность;
- предупредить о несовместимости, нехватке параметров или рисках;
- дать ссылки на товары, категории, документацию;
- при необходимости свериться с внешним каталогом поставщика по наличию;
- работать текстом и голосом.

Пример сценария:

> Пользователь: “Нужно резервное питание для роутера и ONU на 8 часов.”

Помощник должен уточнить мощность устройств, напряжение питания, желаемое время автономии, бюджет, затем предложить ДБЖ/аккумулятор/готовый комплект и объяснить расчёт.

## 2. Где размещается помощник

### 2.1. AI-персонаж на сайте

На сайте должен быть не просто floating button, а разработанный анимированный персонаж-консультант Elektronom.

Формат: маленький технический робот/AI-ассистент, который визуально выглядит как часть бренда Elektronom и ведёт себя как живой консультант магазина.

Роль персонажа:

- встречает пользователя;
- показывает, что умеет помочь с подбором;
- реагирует на действия пользователя;
- “изучает каталог” во время поиска;
- “читает документацию” во время технической проверки;
- “пишет ответ” во время генерации;
- “говорит” во время голосового ответа.

Это не должна быть статическая иконка в круге. Персонаж должен иметь набор состояний и коротких сценариев анимации.

Размещение:

- расположение: правый нижний угол desktop, над mobile bottom nav на мобильных;
- размер персонажа на desktop: ориентировочно 72-96px по высоте в свернутом состоянии;
- размер на mobile: 56-72px, чтобы не перекрывать bottom nav;
- при раскрытии рядом/над персонажем открывается чат-панель;
- персонаж остаётся видимым и меняет состояние в зависимости от сценария.

Не делать навязчивым. Иконка не должна перекрывать корзину, mobile nav, кнопки “добавить в корзину”.

### 2.2. Образ персонажа

Нужно разработать фирменный образ:

- технический робот-консультант;
- не детский мультяшный герой, а аккуратный B2B/B2C ассистент для магазина электротехники;
- визуальная связь с брендом Electronom: синий акцент, элементы электроники, пиксельная/техническая пластика, маленький знак `E` или молния допустимы;
- лицо/экран/визор должен передавать эмоции состояниями;
- персонаж должен хорошо читаться на светлом фоне сайта;
- персонаж должен быть пригоден для SVG/Lottie/Rive-анимации.

Запрещено:

- использовать случайного stock-робота без адаптации под бренд;
- делать слишком крупного персонажа, который мешает покупке;
- делать агрессивную постоянную анимацию;
- использовать тяжёлые видео вместо оптимизированной анимации.

### 2.3. Сценарии анимации персонажа

Нужно реализовать минимум 7 состояний.

#### 1. Greeting / приветствие

Когда пользователь впервые попадает на сайт или проводит 5-8 секунд на странице:

- робот мягко появляется;
- один раз машет рукой;
- показывает короткий bubble:

```text
Допоможу підібрати товар
```

или для RU:

```text
Помогу подобрать товар
```

Bubble должен исчезать сам, без раздражающего поведения.

#### 2. Idle / ожидание

Когда пользователь не взаимодействует:

- лёгкое дыхание/покачивание;
- редкое мигание экрана/глаз;
- мягкий glow раз в несколько секунд;
- без постоянного привлечения внимания.

#### 3. Hover / готов помочь

При наведении на персонажа:

- робот слегка поворачивается к пользователю;
- поднимает руку или подсвечивает экран;
- появляется tooltip:

```text
Підібрати товар
```

#### 4. Searching catalog / изучает каталог

После отправки вопроса, когда система ищет товары:

- робот “листает каталог” или сканирует карточки;
- можно показать маленькие движущиеся карточки/строки рядом с персонажем;
- статус в панели:

```text
Шукаю товари в каталозі...
```

RU:

```text
Ищу товары в каталоге...
```

#### 5. Reading docs / читает документацию

Когда RAG ищет технические документы:

- робот смотрит в планшет/лист/схему;
- вокруг появляются маленькие линии схемы, PDF/document icon или техническая сетка;
- статус:

```text
Перевіряю технічну документацію...
```

#### 6. Thinking / анализирует

Когда Claude формирует вывод:

- робот делает “thinking” состояние;
- экран/глаза меняют выражение;
- допустимы 3 dots, вращение маленькой шестерни или световой индикатор;
- статус:

```text
Порівнюю характеристики...
```

#### 7. Typing / пишет ответ

Когда ответ стримится в чат:

- робот печатает на маленькой клавиатуре/панели;
- в чате появляется streaming text;
- анимация должна быть синхронизирована с появлением ответа.

#### 8. Speaking / говорит

Когда включена озвучка:

- робот показывает состояние speaking;
- рот/экран/световой индикатор анимируется;
- рядом можно показать маленький audio wave;
- пользователь может остановить голос.

#### 9. Error / не могу проверить

Если Claude/API/документы/остатки недоступны:

- робот не должен выглядеть “сломавшимся” пугающе;
- показать спокойное состояние warning;
- bubble:

```text
Не вдалося перевірити всі джерела. Можу передати менеджеру.
```

### 2.4. Технический формат анимации

Рекомендуемые варианты реализации:

- Rive для интерактивного state machine персонажа;
- Lottie для простых сценариев;
- SVG + CSS animation для MVP;
- Canvas/WebGL не использовать без необходимости.

Предпочтительно:

- один character component;
- state machine: `greeting`, `idle`, `hover`, `searching`, `readingDocs`, `thinking`, `typing`, `speaking`, `error`;
- переключение состояний из логики assistant panel;
- lazy-load анимационного ассета, чтобы не утяжелять первый экран.

Файлы:

```text
src/components/assistant/assistant-character.tsx
src/components/assistant/assistant-character-state.ts
public/assistant/character.riv
```

или для Lottie:

```text
public/assistant/robot-greeting.json
public/assistant/robot-idle.json
public/assistant/robot-searching.json
public/assistant/robot-reading-docs.json
public/assistant/robot-typing.json
public/assistant/robot-speaking.json
```

### 2.5. Связь персонажа с чатом

Персонаж не просто открывает чат, а отражает этап работы помощника.

Пример последовательности:

1. Пользователь открывает страницу.
2. Через 5 секунд робот машет рукой.
3. Пользователь кликает на робота.
4. Открывается панель чата.
5. Пользователь пишет: “подбери ДБЖ для роутера”.
6. Робот переходит в `searching`.
7. Система ищет товары.
8. Робот переходит в `readingDocs`.
9. Система ищет технические материалы.
10. Робот переходит в `thinking`.
11. Claude формирует ответ.
12. Робот переходит в `typing`.
13. Ответ появляется в чате.
14. Если пользователь нажал “озвучить”, робот переходит в `speaking`.

Это должно быть описано и реализовано как сценарий, а не как случайные CSS-анимации.

### 2.6. Страница помощника

Дополнительно создать отдельную страницу:

```text
/uk/assistant
/ru/assistant
```

На этой странице можно дать более широкий интерфейс:

- большая история диалога;
- карточки предложенных товаров;
- фильтры;
- список источников;
- кнопка “отправить подбор в корзину”;
- кнопка “создать заявку/КП”.

## 3. Пользовательские сценарии

### 3.1. Подбор товара по задаче

Пользователь описывает задачу:

- “какой автомат поставить на бойлер 2 кВт”;
- “подбери аккумулятор для инвертора”;
- “какой кабель нужен для 5 кВт на 30 метров”;
- “что нужно для видеонаблюдения на склад”;
- “хочу комплект резервного питания для дома”.

Помощник:

1. классифицирует задачу;
2. определяет категорию;
3. задаёт уточняющие вопросы;
4. делает расчёт или техническую проверку;
5. предлагает 2-4 варианта товара;
6. объясняет различия;
7. показывает наличие;
8. даёт CTA: “Открыть товар”, “Добавить в корзину”, “Сформировать КП”.

### 3.2. Консультация по совместимости

Пользователь спрашивает:

- “подойдёт ли этот аккумулятор к этому инвертору?”;
- “можно ли ставить этот автомат на такую нагрузку?”;
- “совместима ли камера с этим регистратором?”.

Помощник должен:

- запросить недостающие параметры;
- сверить характеристики;
- показать результат: совместимо / условно совместимо / не рекомендуется;
- объяснить техническую причину;
- предложить альтернативу.

### 3.3. Объяснение характеристик

Пользователь спрашивает:

- “что значит C16?”;
- “чем AGM отличается от LiFePO4?”;
- “что такое DPDT?”;
- “почему нужен УЗО?”.

Помощник отвечает простым языком, но технически корректно, со ссылками на товары и документацию.

### 3.4. Сравнение товаров

Пользователь выбирает 2-4 товара и просит сравнить.

Помощник должен:

- построить сравнение по важным характеристикам;
- выделить плюсы/минусы;
- объяснить, кому какой вариант подходит;
- не советовать товар без наличия, если есть доступная альтернатива.

### 3.5. Проверка наличия

Если товар есть в каталоге, но остаток неизвестен/сомнителен:

- помощник должен проверить внутренний файл остатков;
- при необходимости свериться с API/каталогом поставщика;
- явно указать статус:
  - `В наявності`;
  - `Під замовлення`;
  - `Потрібне уточнення`;
  - `Немає в наявності`.

## 4. Источники знаний

Помощник должен отвечать не “из головы”, а через базу знаний и каталог.

### 4.1. Внутренний каталог Elektronom

Источник:

- товары;
- категории;
- бренды;
- характеристики;
- цены;
- остатки;
- изображения;
- аналоги;
- совместимые аксессуары;
- связанные товары.

Данные должны подтягиваться из текущей БД/поискового индекса. Если используется Prisma, соблюдать правила проекта:

- только `@/lib/prisma`;
- коллекции только с `take/skip`;
- `select` вместо широкого `include`;
- не раскрывать себестоимость, админские поля, внутренние токены.

### 4.2. Файл остатков

На сервере должен быть подключаемый источник остатков:

```text
data/inventory/
```

Форматы:

- `.csv`;
- `.xlsx`;
- `.json`;
- API поставщика, если доступен.

Минимальные поля:

```text
sku
mpn
supplierSku
name
stock
warehouse
price
updatedAt
supplierName
```

Нужно реализовать нормализацию SKU/MPN, чтобы помощник мог сопоставить товар сайта с остатками поставщика.

### 4.3. Техническая документация

На сервере должна быть база материалов:

```text
data/technical-docs/
```

Типы документов:

- PDF-инструкции;
- datasheet;
- схемы подключения;
- сертификаты;
- таблицы совместимости;
- статьи;
- внутренние методички;
- FAQ для менеджеров.

Нужно реализовать ingestion pipeline:

1. загрузка документа;
2. извлечение текста;
3. разбиение на chunks;
4. сохранение embeddings;
5. привязка к категориям/брендам/SKU;
6. индексирование для поиска.

### 4.4. Каталог поставщика

Если поставщик даёт API:

- использовать API;
- хранить credentials только на сервере;
- делать rate limiting;
- кешировать ответы;
- логировать время последней проверки.

Если API нет:

- использовать только разрешённые способы проверки;
- не строить хрупкий scraping без согласования;
- лучше сначала поддержать ручной импорт прайса/остатков.

Важно: AI должен честно говорить “потрібне уточнення”, если источник наличия недоступен.

## 5. AI-архитектура

### 5.1. LLM provider

Основной провайдер: Claude API.

Все запросы к Claude выполняются только на сервере:

```text
src/app/api/assistant/chat/route.ts
```

Запрещено:

- хранить API key на клиенте;
- отдавать prompt/system instructions в браузер;
- отправлять в Claude лишние персональные данные пользователя.

### 5.2. RAG pipeline

Перед ответом помощник должен:

1. классифицировать запрос;
2. найти релевантные товары;
3. найти релевантные документы;
4. проверить остатки;
5. сформировать контекст для Claude;
6. получить ответ;
7. провалидировать ответ на ссылки/товары/наличие;
8. вернуть пользователю структурированный ответ.

Ответ должен содержать:

- короткий вывод;
- уточняющие вопросы, если данных недостаточно;
- 2-4 рекомендованных товара;
- техническое объяснение;
- источники;
- предупреждения/ограничения;
- CTA.

### 5.3. Skill технического консультанта

Нужно оформить внутреннюю инструкцию/skill для помощника.

Поведение skill:

- сначала анализировать задачу;
- не подбирать товар без ключевых параметров;
- если параметров не хватает, задавать максимум 2-4 уточняющих вопроса;
- не выдумывать наличие;
- не выдумывать характеристики;
- если данные из документации и каталога конфликтуют, явно указать конфликт;
- для опасных электротехнических решений давать предупреждение “потребує перевірки спеціалістом”;
- не давать инструкции, которые могут привести к опасному монтажу без квалификации.

Пример системной роли:

```text
Ты технический консультант интернет-магазина Elektronom.
Твоя задача - помочь подобрать товар из каталога, используя только предоставленный каталог, остатки и техническую документацию.
Если данных недостаточно - задай уточняющие вопросы.
Не выдумывай наличие, цены, характеристики и совместимость.
```

## 6. Голосовой режим

### 6.1. Голосовой ввод

В чате должна быть кнопка микрофона.

Поведение:

- пользователь нажимает микрофон;
- браузер запрашивает доступ к microphone;
- начинается запись;
- UI показывает активную запись;
- запись преобразуется в текст;
- текст вставляется в поле ввода;
- пользователь может отправить или автоотправка после паузы.

Рекомендуемые варианты:

- Web Speech API для MVP;
- серверная speech-to-text интеграция для production, если качество Web Speech недостаточно.

### 6.2. Озвучивание ответа

После ответа помощник может синтезировать речь.

Поведение:

- рядом с ответом кнопка “прослушать”;
- если голосовой режим активен, ответ озвучивается автоматически;
- пользователь может остановить озвучивание;
- иконка робота показывает состояние speaking.

Рекомендуемые варианты:

- Web Speech API для MVP;
- внешний TTS provider для более качественного голоса на production.

### 6.3. Языки

Минимум:

- украинский;
- русский.

Помощник должен отвечать на языке текущей локали сайта, но если пользователь пишет на другом языке, можно отвечать на языке пользователя.

## 7. UI/UX

### 7.1. Виджет

Состояния:

- closed;
- open;
- listening;
- thinking;
- speaking;
- error;
- offline/limited.

Визуально:

- иконка робота в стиле Elektronom;
- не мультяшная игрушка, а технологичный помощник;
- мягкая анимация;
- аккуратный синий акцент;
- без агрессивных градиентов;
- не перекрывать важные элементы сайта.

### 7.2. Чат-панель

Внутри:

- история сообщений;
- история должна быть прокручиваемой, помощник не должен терять контекст предыдущих сообщений;
- пользователь должен иметь возможность вернуться выше по диалогу и открыть ранее предложенные товары/сравнения;
- поле ввода;
- кнопка микрофона;
- кнопка отправки;
- быстрые подсказки:
  - “Підібрати ДБЖ”
  - “Підібрати автомат”
  - “Порівняти товари”
  - “Пояснити характеристику”
- карточки товаров в ответе;
- ссылки на источники;
- индикатор “проверяю документацию / остатки”.

### 7.3. Вкладка живого заказа / подборки

Кроме чата, помощник должен уметь раскрывать перед пользователем отдельную рабочую вкладку/панель, где онлайн формируется подборка или заказ.

Название в UI:

- `Підбір`;
- `Замовлення`;
- `Комерційна пропозиція`;
- для RU: `Подбор`, `Заказ`, `Коммерческое предложение`.

Эта панель должна работать как “живой черновик заказа”, который меняется по командам пользователя.

Примеры команд:

```text
добавь это в заказ
замени аккумулятор на дешевле
сравни этот вариант с LiFePO4
убери генератор
добавь кабель и автомат
сохрани подбор
сформируй КП
```

Панель заказа должна показывать:

- список выбранных товаров;
- количество;
- цену за единицу;
- сумму по строке;
- наличие;
- техническую роль товара в решении;
- предупреждения по совместимости;
- общую сумму внизу;
- статус: `черновик`, `проверяется`, `готово`, `нужно уточнение`.

Итоговая сумма должна пересчитываться автоматически при каждом изменении:

```text
Разом: 12 480 грн
```

Если есть доставка/скидка/НДС, показывать отдельными строками, но не выдумывать значения без данных.

### 7.4. Сценарий сравнения и замены товара

Если пользователь пишет “замени”, “сравни”, “что лучше”, “подбери аналог”, рядом с текущим заказом должно открываться второе похожее окно сравнения.

Структура:

```text
┌──────────────────────────┐    ┌──────────────────────────┐
│ Старый заказ / вариант A │ -> │ Новый заказ / вариант B  │
│ текущие товары           │    │ предложенная замена      │
│ старая сумма             │    │ новая сумма              │
└──────────────────────────┘    └──────────────────────────┘
        [Отклонить]                 [Принять замену]
```

Обязательно:

- показать старый товар и новый товар;
- показать разницу в цене;
- показать разницу в характеристиках;
- показать наличие нового товара;
- объяснить, почему предлагается замена;
- показать риск, если замена хуже по параметрам;
- дать кнопки:
  - `Прийняти`;
  - `Відхилити`;
  - `Порівняти детальніше`;
  - `Запитати менеджера`.

Пример:

```text
Заміна: AGM 20Ah -> LiFePO4 20Ah
Різниця: +1 250 грн
Плюси: більший ресурс, менша вага, краща глибина розряду
Мінуси: дорожче
```

### 7.5. Анимация применения замены

Если пользователь нажимает `Прийняти` / `Сохранить`:

1. старая строка товара мягко подсвечивается;
2. рядом появляется стрелка замены;
3. новый товар “переезжает” в основной заказ;
4. старое окно сравнения закрывается;
5. остаётся одно окно текущего заказа;
6. сумма внизу плавно пересчитывается;
7. помощник кратко подтверждает действие в чате.

Пример подтверждения:

```text
Готово, замінив AGM на LiFePO4. Сума підбору оновлена: 13 730 грн.
```

Если пользователь нажимает `Відхилити`:

- окно нового варианта закрывается;
- текущий заказ остаётся без изменений;
- помощник предлагает другой вариант или спрашивает критерий замены.

### 7.6. Черновик, корзина и КП

Живой заказ не должен сразу ломать реальную корзину пользователя.

Рекомендуемая логика:

- AI сначала формирует `draft selection`;
- пользователь может править подбор;
- после подтверждения нажимает:
  - `Додати все в кошик`;
  - `Зберегти підбір`;
  - `Сформувати КП`;
  - `Надіслати менеджеру`.

Только после явного действия пользователя товары попадают в корзину или создаётся заявка/КП.

Если пользователь авторизован:

- можно сохранить подбор в аккаунт;
- можно связать с заказом/заявкой.

Если пользователь гость:

- сохранять в session/local draft;
- предложить отправить на email/phone или войти.

### 7.7. Карточка рекомендованного товара

Карточка в ответе должна показывать:

- изображение;
- название;
- SKU/MPN;
- ключевые характеристики;
- цену;
- наличие;
- причину рекомендации;
- кнопки:
  - открыть товар;
  - добавить в корзину;
  - добавить в подбор;
  - заменить в подборе;
  - сравнить;
  - задать вопрос по товару.

## 9. Логи и аналитика

Логировать:

- запрос пользователя;
- язык;
- найденные товары;

- был ли ответ полезен;

Не логировать:

## 10. Безопасность

Обязательные требования:

- Claude API key только на сервере;
- rate limiting на API помощника;
- защита от prompt injection;
- не позволять пользователю заставить AI раскрыть system prompt;
- фильтровать документы, которые можно использовать как источник;
- не давать опасные монтажные инструкции как окончательное руководство;
- для электротехнических решений добавлять дисклеймер о необходимости проверки специалистом.

Пример:

```text
Перед монтажом електрообладнання перевірте рішення з кваліфікованим електриком.
```

### 11.3. API response format

Ответ API должен быть структурированным:

```ts
type AssistantResponse = {
  message: string
  questions?: string[]
  products?: RecommendedProduct[]
  draftOrder?: AssistantDraftOrder
  orderComparison?: AssistantOrderComparison
  sources?: AssistantSource[]
  warnings?: string[]
  availabilityCheckedAt?: string
}
```

Не отдавать просто “сырой текст от Claude” без структурирования.

Для живого заказа нужны отдельные типы:

```ts
type AssistantDraftOrder = {
  id: string
  status: 'draft' | 'checking' | 'ready' | 'needs_review'
  items: AssistantDraftOrderItem[]
  subtotal: number
  discount?: number
  tax?: number
  total: number
  currency: 'UAH'
  warnings?: string[]
}

type AssistantOrderComparison = {
  mode: 'replace' | 'compare' | 'alternative'
  previousOrder: AssistantDraftOrder
  proposedOrder: AssistantDraftOrder
  changedItems: AssistantOrderChange[]
  priceDelta: number
  technicalSummary: string
  recommendation: 'accept' | 'reject' | 'needs_manager_review'
}
```

Важно: цены и суммы должны считаться на сервере по актуальным данным каталога/остатков, а не доверяться ответу Claude.

1. Помощник открывается с сайта как виджет.
2. Есть отдельная страница `/uk/assistant` и `/ru/assistant`.

4. Помощник задаёт уточняющие вопросы, если данных мало.
5. Помощник предлагает товары из реального каталога.
6. В ответе есть карточки товаров с ссылками.
7. Ответы учитывают наличие/остатки, если источник доступен.

9. Claude API key не попадает на клиент.
10. Есть прокручиваемая история чата, где можно вернуться к старым рекомендациям.

## 14. Что не делать

- Не делать помощника как декоративный чат без связи с каталогом.
- Не выдумывать цены, наличие и характеристики.
- Не отправлять Claude весь каталог целиком.
- Не хранить Claude API key в `NEXT_PUBLIC_*`.
- Не давать опасные электротехнические инструкции без предупреждения.
- Не делать голос обязательным для использования.
- Не блокировать покупку, если помощник недоступен.
- Не смешивать внутренние админские данные с публичным ответом.

## 15. Важное продуктовое требование

Помощник должен продавать через консультацию, а не просто болтать.

Хороший ответ помощника:

- уточняет задачу;
- объясняет технически;
- предлагает конкретные товары;
- показывает наличие;
- даёт понятный следующий шаг.

Плохой ответ:

- общая статья без товаров;
- рекомендации без ссылок;
- “может подойти” без проверки параметров;
- выдуманные характеристики;
- игнорирование наличия.
