# Диагностика: пустые карточки товара и медленная загрузка категорий

> Дата: 2026-06-03. Тип: root-cause анализ по фактическому коду (read-only).
> Файлы: `src/app/[locale]/(shop)/catalog/[slug]/page.tsx`, `src/queries/products.ts`, `src/queries/categories.ts`, `src/components/shared/transparent-image.tsx`, `src/components/product/product-card.tsx`.

## TL;DR — одна причина на оба симптома

**Страница категории в одном `await Promise.all([...])` ждёт И сетку товаров, И расчёт фасетов — без единого `<Suspense>`. Расчёт фасетов (`getCategoryFacets`) — некэшируемая, выполняемая на КАЖДЫЙ запрос in-memory свёртка, которая грузит до 50 000 товаров и крутит вложенные циклы ≈ O(числo_опций_фасетов × товары × ключи_атрибутов). Для крупных родительских категорий (`elektryka` ≈ 3816 товаров с богатыми атрибутами) это десятки секунд … >300с. Так как это в одном `await` с гридом и нет стриминга — пока фасеты не досчитались, НЕ рендерится НИЧЕГО: ни одной карточки. Отсюда «пустой каталог» и «медленные группы».**

Сетка сама по себе быстрая и корректная — её держит в заложниках расчёт фасетов.

## Доказательства (file:line)

### 1. Грид заблокирован фасетами — `catalog/[slug]/page.tsx:152-171`
```ts
const [{ products, total }, facets] = await Promise.all([
  getFilteredProducts({ categorySlug: slug, … }),   // быстро, 24 товара
  getCategoryFacets({ categorySlug: slug, … }),      // ТЯЖЁЛО, до 50k товаров в памяти
])
```
- Это **единый async-RSC** без `<Suspense>` нигде вокруг грида/сайдбара → рендер «всё или ничего».
- `Promise.all` не делает быстрее: общий await завершится по **самому медленному** (фасеты). Грид ждёт фасеты.
- Нет `loading`-стриминга для грида: до резолва Promise.all страница не отдаёт карточки.

### 2. Фасеты грузят до 50 000 товаров в память — `categories.ts:203-243`
`getCategoryProductsForFacets`: `take: 50000`, тянет `attributes` (JSONB), brand, price, stock по всему поддереву. Комментарий самого дева: *«In-memory MVP Facets calculation limit … loads up to 50,000 items»*.

### 3. Свёртка фасетов — O(опции × товары × ключи), НЕ кэширована — `categories.ts:245-485`
- У `getCategoryFacets` **нет** `'use cache'` → пересчёт на каждый запрос и на каждый клик фильтра.
- Секция атрибутов (439-469): для **каждого** значения каждого ключа — проход по **всем** товарам с вызовом `matchProduct` (который сам в цикле проверяет все активные ключи). Для elektryka это легко десятки миллионов операций на запрос. Это и есть наблюдавшийся таймаут ~300с.
- Секция брендов (418-435): O(бренды × товары).

### 4. Данные и запрос грида — В ПОРЯДКЕ (исключаем ложные гипотезы)
- `getFilteredProducts` (products.ts:323-332) фильтрует по **поддереву**: `categoryIds = getCategorySubtreeIds(slug)` → `where.categoryId IN categoryIds`. `total = prisma.product.count({ where })` по тому же поддереву.
- Счётчик меню «3816» = `getCategoryTree._count.products` (isActive), сумма по поддереву (categories.ts:112-161). Раз меню показывает 3816 — значит 3816 активных товаров **реально привязаны** к поддереву `elektryka`. Тот же фильтр в гриде их вернёт.
- ⇒ Гипотезы H1 (прямой слаг в листинге), H3 (рассинхрон слагов импорта) — **опровергнуты** текущим кодом. Запрос корректен.

### 5. Рендер карточки/изображения — уже НЕ тяжёлый (H2 снят)
- `transparent-image.tsx:1-32` — тонкая обёртка над `next/image`, **без canvas/BFS**. Старый per-card INP-killer дев убрал.
- ⇒ H2 (краш/тяжесть рендера карточки) — не актуально. Блокировка идёт от фасетов, а не от карточек.

## Что уже починено (НЕ переделывать)
- ✅ Поддерево в листинге (`getFilteredProducts`) и в счётчиках.
- ✅ Привязка данных (товары в поддереве категорий).
- ✅ Canvas-обработка убрана с рендера (`TransparentImage` → `next/image`).
- ✅ Белый экран товара (ERR_REQUIRE_ESM) — отдельно, через переход на `sanitize-html`.

## Рекомендации по фиксу (приоритет)

### FIX-1 🔴 Развязать грид и фасеты через стриминг (Suspense)
В `page.tsx`: рендерить `<ProductGrid>` из `getFilteredProducts` **сразу**; всё, что зависит от `facets` (сайдбар `CatalogFilters`, фасетные части `CatalogToolbar`, лейблы пилюль), вынести в дочерний async-компонент в `<Suspense fallback={<FiltersSkeleton/>}>`.
- `total` для H1/тулбара берётся из `getFilteredProducts` (быстро) — оставить.
- Результат: карточки появляются <1с; фильтры «дотекают» позже. Даже медленные фасеты больше **не** оставляют каталог пустым.

### FIX-2 🔴 Убрать in-memory свёртку фасетов (настоящее лечение скорости)
Заменить `getCategoryProductsForFacets` (take:50000) на агрегаты:
- **Стратегически:** нативные фасеты **Algolia** (уже интегрирована в проекте) — движок считает фасеты при скейле.
- **Прагматично сейчас:** агрегация в Postgres через `$queryRaw` (`GROUP BY brand`, `jsonb_each_text` для атрибутов, `width_bucket`/гистограмма для цены) — возвращать **только счётчики**, а не 3816 строк.
- Минимум-стоп-гэп: добавить `'use cache'` к `getCategoryFacets` по ключу (slug, activeFilters) + снизить `take` — но это слабее (низкий hit-rate по комбинациям фильтров). SQL/Algolia — правильно.

### FIX-3 🟡 Индексы БД (опора для FIX-2 и грида)
- `Product(categoryId, isActive)` — для `categoryId IN (поддерево) AND isActive` + `count`.
- `Product(sortOrder)`, `Product(price)` — для `orderBy`.
- **GIN** на `Product.attributes` (jsonb) — для атрибутных фильтров (`path/equals/array_contains` в `buildAttributeWhere`); без него — full scan.

### FIX-4 🟢 Кэшировать `getCategorySubtreeIds`
Сейчас вызывается **2×/запрос** (в `getFilteredProducts` и в `getCategoryProductsForFacets`), каждый раз грузит ВСЕ категории. Обернуть `'use cache'` (cacheLife hours, cacheTag `categories`) по ключу slug.

## Порядок внедрения
**FIX-2** (снять 300с-свёртку) → **FIX-1** (стриминг — пуленепробиваемость грида) → **FIX-3** (индексы) → **FIX-4** (мелочь). FIX-1+FIX-2 вместе закрывают оба симптома: карточки появляются сразу, группы грузятся быстро.

## Что НЕ является причиной (чтобы не гонять зря)
- Не sitemap, не редиректы, не таксономия, не bg-removal на рендере, не санитайзер, не привязка данных. Всё это — отдельные (уже закрытые либо несвязанные) темы. Корень — синхронный тяжёлый расчёт фасетов, блокирующий рендер.
