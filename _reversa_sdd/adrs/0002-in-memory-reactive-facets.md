# ADR-0002 — Реактивные фасеты считаются in-memory (MVP)

**Статус:** Принято (MVP, требует пересмотра при масштабировании) · 🟢 подтверждено кодом/комментарием

## Контекст
Нужны реактивные счётчики фильтров (как на Rozetka): кол-во товаров у каждой опции с учётом прочих активных фильтров. Агрегация по JSONB-атрибутам в SQL сложна.

## Решение
`getCategoryProductsForFacets` загружает до **50 000** активных товаров категории, а `getCategoryFacets` считает все счётчики/гистограмму цен (32 бакета) **в памяти Node**, зеркаля SQL-логику фильтра (`matchProduct` с `excludeKey`). Результат кэшируется (`cacheLife('minutes')`).

## Последствия
- ➕ Простая, точная и реактивная логика без сложного SQL.
- ➖ Жёсткий потолок 50k и нагрузка на память/CPU при больших категориях (🔴 C-1).
- ➖ **Дублирование логики** с SQL-фильтром списка (`buildProductWhere`) → риск расхождения выдачи и счётчиков (🟡 C-2).

## План эволюции (из комментария в коде)
1. SQL-агрегация через `$queryRaw` + `jsonb_each_text`.
2. Перенос фасетов в Algolia/Meilisearch/Elasticsearch (Algolia уже подключён).
