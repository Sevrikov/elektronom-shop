# Задача для Claude Code / Reversa: ревью мобильной совместимости Elektronom

## Режим работы

Провести **только ревью мобильной совместимости** сайта Elektronom.

Не вносить изменения в код без отдельного разрешения.

Результат работы: подробный Markdown-отчёт для разработчика с найденными проблемами, приоритетами, рекомендациями и чеклистом приёмки.

Дополнительно: если в окружении доступны инструменты автоматизации браузера, использовать их для подтверждения выводов скриншотами и базовыми проверками. Если инструментов нет, провести ручное/визуальное ревью и явно отметить это в отчёте.

## Главная цель

Проверить, насколько мобильная версия сайта готова к реальному использованию покупателем.

Фокус не на “красиво/некрасиво” в общем смысле, а на том, может ли пользователь с телефона:

- найти товар;
- открыть каталог;
- отфильтровать товары;
- открыть карточку товара;
- посмотреть изображения;
- добавить товар в корзину;
- изменить количество;
- оформить заказ;
- войти/зарегистрироваться;
- вернуться к нужной странице без путаницы.

## Рекомендуемые инструменты проверки

Использовать доступные инструменты в таком приоритете:

1. **Playwright / browser automation**
   - открыть страницы на заданных viewport;
   - сделать screenshots;
   - проверить horizontal overflow;
   - проверить видимость ключевых CTA;
   - проверить кликабельность основных кнопок;
   - проверить открытие/закрытие меню, фильтров, cart drawer, gallery lightbox.

2. **Chrome DevTools Device Mode**
   - ручная проверка адаптива;
   - проверка touch-friendly UI;
   - проверка safe-area и bottom navigation.

3. **Lighthouse**
   - mobile performance;
   - accessibility;
   - SEO;
   - best practices.

4. **axe-core / accessibility checker**
   - aria-label;
   - контраст;
   - label для форм;
   - keyboard/focus issues.

5. **Visual regression screenshots**
   - если доступны Percy, Chromatic, Argos CI или похожие инструменты, сохранить сравнимые screenshots;
   - если недоступны, сохранить обычные screenshots по viewport.

6. **BrowserStack / LambdaTest**
   - если есть доступ, выборочно проверить реальный iPhone и Android;
   - если доступа нет, отметить, что проверка выполнена только через viewport emulation.

## Возможный Reversa/Claude mobile skill workflow

Если используется Reversa или похожий AI-review workflow, выполнить ревью как отдельный мобильный модуль:

1. `Discovery`
   - определить ключевые пользовательские сценарии;
   - определить mobile breakpoints;
   - определить компоненты, влияющие на mobile UX.

2. `Viewport Pass`
   - открыть все ключевые страницы на заданных viewport;
   - зафиксировать screenshots;
   - отметить layout breakages.

3. `Interaction Pass`
   - проверить меню;
   - поиск;
   - фильтры;
   - карточку товара;
   - галерею;
   - корзину;
   - checkout.

4. `Accessibility Pass`
   - проверить tap targets;
   - labels;
   - focus;
   - contrast;
   - aria-label для icon-only buttons.

5. `Performance Pass`
   - проверить тяжёлые изображения;
   - layout shift;
   - лишние client components;
   - медленные реакции интерфейса.

6. `Developer Report`
   - сгруппировать findings по P0/P1/P2/P3;
   - указать предполагаемые файлы;
   - сформировать acceptance checklist.

Этот workflow можно в будущем оформить как отдельный локальный skill: `mobile-ux-review`.

## Важное ограничение

Не переписывать код.

Не делать самостоятельный редизайн.

Не менять компоненты, стили, данные, зависимости, миграции или конфиги.

Нужно именно найти проблемы, описать их и подготовить понятное ТЗ для разработчика.

## Тестовые viewport

Проверить минимум следующие размеры:

- `360x740` — маленький Android;
- `375x812` — iPhone mini / compact;
- `390x844` — типичный современный iPhone;
- `430x932` — крупный смартфон;
- `768x1024` — планшет / iPad portrait.

Если есть возможность, дополнительно проверить:

- `414x896`;
- `412x915`;
- `1024x768` tablet landscape.

## Что проверять на каждой странице

### 1. Горизонтальный скролл

Проверить, нет ли непреднамеренного горизонтального скролла.

Если есть:

- указать страницу;
- viewport;
- какой элемент расширяет страницу;
- предполагаемый компонент/файл;
- как исправить.

### 2. Header

Проверить:

- логотип не обрезается;
- поиск доступен;
- иконки не налезают друг на друга;
- кнопка меню работает, если есть;
- язык/аккаунт/корзина не создают визуального шума;
- sticky header не перекрывает контент.

### 3. Bottom navigation

Проверить:

- не перекрывает ли bottom nav кнопки и формы;
- счётчик корзины отображается корректно;
- активные/неактивные состояния понятны;
- ссылки ведут на корректные страницы;
- на iOS safe-area не ломает нижнюю навигацию.

### 4. Главная страница

Проверить:

- первый экран;
- категории;
- промо/hero-блоки;
- топ-продажи;
- новые товары;
- B2B CTA;
- footer.

Особое внимание:

- нет ли слишком крупных блоков;
- не пропадает ли главный смысл страницы;
- не ломаются ли карточки товаров;
- удобно ли скроллить.

### 5. Каталог

Проверить:

- список товаров;
- карточки товара;
- сортировку;
- фильтры;
- переходы в категории;
- поиск/пустые состояния;
- пагинацию или “показать ещё”, если есть.

Особое внимание:

- фильтры должны быть доступны на мобильном без перегруза;
- карточки товаров не должны быть слишком мелкими;
- кнопка добавления в корзину должна быть кликабельной;
- цена, наличие, название и изображение должны читаться.

### 6. Карточка товара

Проверить:

- H1 и бренд;
- главное изображение;
- галерею;
- открытие изображения / lightbox;
- thumbnails;
- цену;
- наличие;
- SKU;
- quantity stepper;
- кнопку добавления в корзину;
- блоки доставки/гарантии/оплаты;
- характеристики;
- описание;
- отзывы;
- “товары той же серии”;
- “сопутствующие товары”.

Особое внимание:

- не должна ломаться 3-колоночная desktop-структура на мобильном;
- sticky или bottom элементы не должны перекрывать кнопку покупки;
- галерея должна быть удобной пальцем;
- длинные названия и характеристики не должны раздвигать layout;
- похожие товары не должны создавать горизонтальный скролл.

### 7. Корзина

Проверить:

- список товаров;
- изменение количества;
- удаление товара;
- итоговую сумму;
- кнопку checkout;
- пустую корзину;
- cart drawer, если используется;
- синхронизацию счётчика корзины.

Особое внимание:

- кнопка оформления заказа должна быть видимой и доступной;
- bottom nav не должен её перекрывать;
- длинные названия товаров не должны ломать строку;
- quantity stepper должен быть удобным.

### 8. Checkout

Проверить:

- поля формы;
- ошибки валидации;
- выбор доставки;
- выбор оплаты;
- итог заказа;
- кнопку подтверждения;
- поведение клавиатуры на телефоне;
- фокус полей;
- длинные ошибки;
- sticky summary, если есть.

Особое внимание:

- форма должна быть проходима одним пальцем;
- пользователь не должен теряться между полями;
- сообщения об ошибках должны быть видны рядом с полями;
- кнопка submit не должна быть перекрыта bottom nav.

### 9. Авторизация и регистрация

Проверить:

- поля email/password;
- social login, если есть;
- ошибки;
- переходы между login/register;
- возврат на предыдущую страницу после логина;
- удобство на маленьком экране.

### 10. Wishlist и Profile

Проверить:

- empty state;
- список товаров в wishlist;
- переход в карточку товара;
- кнопки удаления/добавления;
- profile navigation;
- заказы пользователя, если есть.

## Проверка интерактивности

Проверить руками:

- открыть/закрыть поиск;
- открыть/закрыть меню;
- добавить товар в корзину;
- открыть cart drawer;
- изменить количество;
- удалить товар;
- перейти в checkout;
- вызвать ошибки формы;
- открыть галерею товара;
- закрыть lightbox;
- перейти через bottom nav;
- вернуться браузерной кнопкой назад.

## Проверка визуального качества

Искать:

- налезание текста;
- обрезанные кнопки;
- слишком мелкие tap targets;
- неравномерные отступы;
- карточки внутри карточек;
- лишние большие радиусы;
- неконсистентные цвета;
- случайные inline-style эффекты;
- плохую читаемость;
- слишком длинные строки;
- несоответствие стилю главной и каталога;
- разные стили похожих кнопок.

## Проверка производительности на мобильном

Проверить:

- не слишком ли тяжёлая первая загрузка;
- не скачиваются ли огромные изображения;
- нет ли прыжков layout при загрузке;
- не блокирует ли UI тяжёлый JavaScript;
- не слишком ли много client components там, где можно server components;
- нет ли медленных действий при добавлении в корзину.

Если возможно, указать:

- LCP-проблемы;
- CLS-проблемы;
- лишний JS;
- тяжёлые изображения;
- проблемные компоненты.

Желательно дополнительно указать:

- используются ли изображения подходящего размера;
- не грузятся ли desktop-sized изображения на mobile;
- не создаёт ли gallery/lightbox лишний JavaScript;
- можно ли часть интерактива оставить на Server Components;
- нет ли ненужных re-render при открытии корзины или изменении количества;
- нет ли слишком тяжёлых third-party scripts.

## Проверка accessibility

Проверить:

- кнопки имеют понятные label/aria-label;
- фокус виден;
- интерактивные элементы доступны клавиатурой;
- контраст текста достаточный;
- кнопки не меньше комфортной зоны нажатия;
- изображения имеют alt;
- формы имеют label/error state.

## Приоритеты замечаний

Разделить находки на уровни:

### P0 Critical blockers

Проблемы, из-за которых пользователь не может купить товар или завершить ключевой сценарий.

Примеры:

- невозможно нажать checkout;
- форма не отправляется;
- кнопка скрыта bottom nav;
- корзина не открывается;
- фильтры полностью недоступны;
- страница ломается на 360px.

### P1 Major UX issues

Проблемы, которые сильно мешают покупке, но есть обходной путь.

Примеры:

- неудобный quantity stepper;
- слишком мелкие карточки;
- галерея неудобна;
- фильтры трудно закрыть;
- ошибки формы плохо видны;
- важная информация слишком низко.

### P2 Visual polish

Проблемы качества интерфейса.

Примеры:

- неравные отступы;
- разные радиусы;
- плохие пустые состояния;
- текст выглядит неаккуратно;
- дизайн карточки отличается от каталога.

### P3 Nice to have

Улучшения, которые можно отложить.

Примеры:

- дополнительные анимации;
- micro-interactions;
- улучшенные skeleton states;
- более богатые preview для товаров.

## Финальный вывод, который нужен от ревьюера

В конце отчёта обязательно дать один из статусов:

- `READY_FOR_MOBILE_FIX_SPRINT` — проблемы найдены, можно отдавать разработчику.
- `BLOCKED_BY_RUNTIME_ERRORS` — сайт невозможно проверить из-за ошибок запуска/роутинга.
- `MOBILE_ACCEPTABLE_WITH_MINOR_FIXES` — серьёзных блокеров нет, нужны мелкие правки.
- `MOBILE_NOT_READY_FOR_PRODUCTION` — мобильная версия не готова к production.
