# ТЗ 04. Design system and styling

Дата: 2026-05-21  
Источник старой версии: `docs/tz/original/ТЗ_часть4_дизайн.md`

## Цель

Сайт должен выглядеть как рабочий B2B/B2C интернет-магазин электротехники: плотный, понятный, быстрый для выбора товара, без декоративной посадочной страницы вместо магазина.

## Tailwind v4

Правила:

- использовать токены и utility-классы Tailwind v4;
- не добавлять произвольные цвета без необходимости;
- не плодить локальные CSS-файлы;
- не использовать inline styles как стандартный способ верстки.

Исключение для `style={{ ... }}` допустимо только для динамического вычисляемого значения, которое нельзя нормально выразить через Tailwind/CSS variable. Такое место должно быть редким и понятным.

## Design tokens из Concept 6 v2

Старое `ТЗ_часть4_дизайн.md` содержит детальную карту CSS-токенов для `globals.css` / `@theme`. Она не удалена: оригинал лежит в `docs/tz/original/ТЗ_часть4_дизайн.md`.

Разработчик должен проверить, что в актуальном Tailwind v4 слое есть эквиваленты:

- color tokens для surface, text, border, accent, danger/success/warning/info;
- spacing/radius/shadow tokens;
- typography tokens;
- container widths;
- component-level tokens для cards, buttons, badges, drawer/header/footer.

Если названия токенов меняются, нужно сохранить визуальный смысл и обновить документацию/компоненты вместе.

## Типографика

Требования из старого ТЗ остаются:

- `Inter` — основной UI-шрифт;
- `Inter Tight` — логотип и display/H1, если подключён через `next/font`;
- `JetBrains Mono` — BOM/SKU/технические списки, если такие блоки используются;
- числа, цены, SKU, MPN и количество — `tabular-nums`;
- hardcoded `<link>` для шрифтов запрещён, использовать `next/font`;
- не масштабировать шрифт через viewport width.

## Визуальный стиль

Требования:

- интерфейс рабочий, не маркетингово-декоративный;
- карточки товаров компактные и читаемые;
- кнопки действий визуально различимы;
- состояния hover/focus/disabled/loading обязательны для интерактивных элементов;
- радиусы умеренные, без чрезмерно округлых UI-элементов;
- иконки использовать из существующей библиотеки, если она уже подключена;
- не делать вложенные карточки внутри карточек.

## Адаптивность

Нужно проверить:

- mobile 360px;
- mobile 390px;
- tablet 768px;
- desktop 1280px;
- wide desktop 1440px+.

На всех размерах:

- текст не перекрывает соседние элементы;
- кнопки не распираются длинным текстом;
- карточки товара сохраняют сетку;
- header и mobile nav работают;
- фильтры каталога доступны и не блокируют контент;
- checkout form остаётся удобной.

## Каталог и карточки товаров

Карточка товара должна содержать:

- изображение;
- название;
- цену;
- наличие;
- ключевые атрибуты, если они помогают выбору;
- рабочую кнопку добавления в корзину;
- ссылку на товар.

Запрещено:

- скрывать реальные действия за декоративными кнопками;
- делать всю карточку Client Component без необходимости;
- использовать placeholder image там, где у товара есть изображение;
- ломать сетку из-за длинного названия.

## Компоненты из старого дизайн-ТЗ

Нужно проверить и довести:

- Button: размеры, variants, disabled/loading/focus;
- ProductCard: image ratio, title clamp, price, compare price, stock badge, add-to-cart;
- Qty Stepper: стабильная ширина, доступные кнопки, min/max;
- Category Sidebar desktop: вложенность, active state, scroll;
- Hybrid Catalog Drawer в hero/catalog zone, если этот паттерн остаётся;
- Value Props Strip: доставка, гарантия, оплата, консультация;
- Stock Badge: in stock, out of stock, limited;
- Search Bar в header: dropdown, debounce, keyboard states;
- Header: 3-строчная desktop структура, если она подтверждена текущим дизайном;
- Footer: контакты, категории, info links, payment/social;
- Mobile Tab Bar: catalog/search/cart/account.

Если какой-то компонент уже реализован иначе, разработчик должен не копировать старую верстку слепо, а сохранить требуемый UX-смысл и соответствие MASTER v1.3.

## Сетки и layout

Требования:

- контейнеры должны быть едиными для страниц магазина;
- product grid адаптируется без overlap;
- section headings имеют единый ритм;
- desktop category/sidebar layout не должен ломать mobile;
- mobile drawer/tab bar не перекрывает checkout CTA и системные кнопки.

## Оптовая логика

Quantity breaks из старого ТЗ не являются P0, если бизнес не подтвердил оптовые цены. Но если поля уже есть в данных или дизайне, UI должен показывать их последовательно: порог количества, цена, активный выбранный диапазон.

## Анимации, бренд и иконки

- transition короткие и функциональные, без лишней декоративности;
- логотип и бренд должны быть стабильными в header/footer/mobile;
- иконки брать из подключённой библиотеки, не плодить ручные SVG без причины;
- новые анимации не должны ухудшать performance и accessibility.

## Pre-footer B2B CTA

Pre-footer B2B CTA из старого ТЗ сохраняется как P1/P2 блок. Он должен вести к реальному действию: контакты, заявка, консультация или B2B-форма, а не быть декоративной полосой без сценария.

## Формы

Для checkout/account/admin:

- labels обязательны;
- ошибки рядом с полями;
- disabled/loading состояния при submit;
- понятное empty state;
- focus ring видимый;
- поля не должны прыгать при ошибках.

## Проверка дизайна

Перед сдачей разработчик должен вручную проверить:

- главную;
- каталог;
- категорию;
- товар;
- корзину;
- checkout;
- account;
- admin;
- search results;
- 404/error pages.

Если менялась вёрстка, к отчёту нужно приложить список проверенных viewport размеров и указать, где остались спорные места.
