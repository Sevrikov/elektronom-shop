# Content Model Decision

## Current State
- Статические статьи описаны в `src/lib/articles.ts` (поля: `slug`, `title`, `summary`, `image`, `readTime`, `date`, `dateModified`, `type`, `categoryKeywords`, `productKeywords`).
- Полные тексты статей хранятся в виде разметки HTML в объекте `articleContents` в `src/app/[locale]/(shop)/blog/[slug]/page.tsx`.
- В БД (`prisma/schema.prisma`) нет моделей для контент-хаба (`Article`, `Author`, `Reviewer`, etc.). Однако присутствуют модели для RAG/ИИ-ассистента: `TechnicalDocument` (метаданные документации) и `DocumentChunk` (векторизованные чанки текста с полем `embedding` типа `Text`).

## Option A: Static Articles MVP
- **Подход:** Использовать текущий статический слой `src/lib/articles.ts` и `articleContents` для хранения контента. Структура расширяется новыми метаданными (например, `dateModified`, `type`) прямо в кодовой базе.
- **Плюсы:**
  - Полная безопасность для базы данных и существующих транзакций.
  - Нет необходимости проводить миграции БД.
  - Простота локального тестирования и валидации.
  - Полный контроль структуры данных на этапе компиляции TypeScript.
- **Минусы:**
  - Любые изменения/добавления статей требуют коммита и деплоя кода разработчиком.

## Option B: Prisma Article/Guide Model
- **Подход:** Создать полноценные таблицы в БД для статей (`Article`), локализованного контента (`ArticleTranslation`) и авторов/редакторов (`Author`) со сложными связями.
- **Плюсы:**
  - Управление контентом через административную панель CMS.
  - Динамическое связывание авторов/рецензентов и генерация полноценной Person разметки.
- **Минусы:**
  - Потенциальные риски при миграциях БД на продакшене.
  - Усложнение архитектуры кэширования Next.js 16 (требуется `'use cache'` + инвалидация тегов).

## Option C: Reuse TechnicalDocument for Guides
- **Подход:** Использовать существующую БД-модель `TechnicalDocument` для хранения обычных статей блога и руководств покупателя.
- **Плюсы:**
  - Единая таблица для всех документов на сайте.
  - Готовый RAG-мост "из коробки".
- **Минусы:**
  - Смешивание семантических контекстов: `TechnicalDocument` спроектирован под техническую документацию (инструкции, даташиты), а статьи блога являются маркетинговыми инструментами с иными метаданными и структурой.

## Recommendation
**Выбрана Option A: Static Articles MVP** для текущей фазы Alpha 1.2.
*Обоснование:*
- Внедрение микроразметки `ArticleSchema` в задаче A12-2.1 уже успешно выполнено на базе статической структуры без усложнения схемы БД.
- Это полностью исключает риски падения базы данных на живом проекте.
- Разделение релиза на фазы: сначала закладывается фундамент за фич-флагами на MVP, а динамический CMS-слой с БД-моделями переносится на последующий этап после мержа и всестороннего тестирования.

## Migration Strategy
Переход к Option B (Prisma) в будущем будет осуществлен в 3 этапа:
1. Создание и применение миграции для таблиц `articles`, `article_translations`, `authors` (с правильной настройкой связей и relation names).
2. Создание seed-скрипта для переноса всех существующих данных из `src/lib/articles.ts` и `articleContents` в новые таблицы БД.
3. Перевод детальных страниц блога на выборку из БД с использованием функции `'use cache'` и инвалидацией тегов кэша по событию обновления статьи.

## RAG Integration Strategy
Даже при использовании Option A (Static MVP), контент статей блога может быть импортирован в RAG-ассистент:
- Фоновый скрипт/сид во время сборки или через выделенный API-endpoint считывает массив `articles` и `articleContents`.
- Для каждой статьи создается запись `TechnicalDocument` (публичный URL статьи временно сохраняется в `fileUrl`, а HTML/text контент статьи — в поле `content`).
- Текст статьи нарезается на чанки и записывается в `DocumentChunk` с расчетом и сохранением соответствующих векторных представлений (embeddings).

## SEO / AEO Requirements
- JSON-LD разметка типа `BlogPosting` должна содержать только валидные и проверенные адреса страниц.
- Ссылка на автора публикации (`Person`) должна добавляться только после внедрения реальных карточек авторов на сайте.
- Для поисковых систем (AEO) статьи должны содержать структурированный разбор популярных вопросов и краткие лаконичные ответы на них (Direct Answer Block).

## Risks
- **Деградация контента:** Отсутствие удобного редактора для контент-менеджеров. Любые правки опечаток или структуры статей требуют коммита в репозиторий.
- **Синхронизация с RAG:** Поскольку контент статический, при ручном обновлении файлов разметки необходимо принудительно перезапускать скрипт векторизации для RAG-ассистента.
