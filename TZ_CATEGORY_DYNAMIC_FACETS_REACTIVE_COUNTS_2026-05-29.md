# ТЗ: реактивные фасеты и честные counts в фильтрах категории

Дата: 2026-05-29  
Проект: Elektronom  
Связанные документы:

- `TZ_CATEGORY_FILTERS_ROZETKA_STYLE_2026-05-26.md`
- `ANALYSIS_ROZETKA_CATEGORY_PAGE_2026-05-26.md`

## 1. Проблема

На странице категории фильтры сейчас могут показывать пользователю ложную доступность вариантов.

Пример:

1. Пользователь открывает категорию.
2. Ставит диапазон цены, например `до 1000 грн`.
3. В списке товаров остаются только товары, подходящие под этот диапазон.
4. Но в фильтрах брендов/характеристик всё ещё видны как доступные premium-бренды или значения, товаров по которым в текущем ценовом диапазоне уже нет.

Это создаёт неправильное ожидание: пользователь думает, что может выбрать бренд/параметр и получить товары, но после выбора получает пустую или резко несогласованную выдачу.

## 2. Цель

Сделать фильтры категории настоящими реактивными фасетами:

- каждый фильтр должен пересчитываться относительно уже выбранных фильтров;
- недоступные значения должны становиться disabled или визуально явно недоступными;
- count рядом со значением должен показывать, сколько товаров будет доступно при выборе этого значения;
- выбранные значения всегда должны оставаться видимыми, чтобы пользователь мог их снять;
- логика должна работать одинаково на desktop sidebar и mobile drawer.

## 3. Ключевой принцип фасетного расчёта

Для каждой группы фильтра counts считаются по формуле:

```text
base category filter
+ все активные фильтры других групп
- текущая группа фильтра
```

Это стандартная логика marketplace-фасетов.

Пример:

```text
Активно:
- price: 500-1000
- brand: Castrol
- viscosity: 5W-30
```

Для группы `brand` counts считаются с учётом:

```text
category + price + viscosity
```

Но без текущего `brand`, чтобы пользователь видел альтернативы брендов внутри того же набора условий.

Для группы `viscosity` counts считаются с учётом:

```text
category + price + brand
```

Но без текущей `viscosity`.

Для всех остальных групп price-range должен учитываться обязательно.

## 4. Поведение UI

### 4.1 Значения с count > 0

Показывать как доступные:

```text
[ ] Schneider Electric (12)
[ ] ABB (8)
[ ] Hager (3)
```

Клик доступен.

### 4.2 Значения с count = 0

Не показывать как доступные.

Допустимые варианты UX:

1. Показывать disabled и приглушённым цветом:

```text
[ ] Premium Brand (0)
```

2. Либо переносить вниз списка в collapsed-зону “Недоступно при текущих фильтрах”.

Рекомендуемый MVP: disabled + muted + count `0`.

Требования:

- disabled option нельзя выбрать кликом;
- cursor должен быть `not-allowed`;
- текст и count должны быть приглушены;
- tooltip или title желательно: `Недоступно при текущих фильтрах`.

### 4.3 Уже выбранное значение с count = 0

Если значение уже выбрано, оно не должно исчезать.

Показывать его как selected, но с предупреждением:

```text
[x] Premium Brand (0)
```

Пользователь должен иметь возможность снять этот фильтр.

Это важно для случаев, когда комбинация фильтров стала пустой после изменения цены или другого параметра.

### 4.4 Active chips

Active chips должны оставаться источником правды:

```text
[500-1000 грн ×] [Castrol ×] [5W-30 ×]
```

При удалении chip:

- URL обновляется;
- выдача пересчитывается;
- counts всех фасетов пересчитываются;
- disabled-состояния обновляются.

## 5. Цена и range-фильтры

### 5.1 При изменении цены

Когда пользователь меняет price slider или поля цены:

- после debounce 300-500 мс обновить URL;
- сбросить `page=1`;
- пересчитать выдачу;
- пересчитать brand counts;
- пересчитать attribute counts;
- disabled-состояния всех остальных фильтров должны измениться.

### 5.2 Price range source

Для price-фильтра хранить два понятия:

```ts
absolutePriceRange: { min: number; max: number } // вся категория
availablePriceRange: { min: number; max: number } // текущие фильтры без price
selectedPriceRange: { min?: number; max?: number } // из URL
```

MVP допускает один range по категории, но counts других фильтров обязаны учитывать выбранную цену.

Лучше:

- slider rail показывает absolute range категории;
- подсказка/границы “доступно при текущих фильтрах” берутся из `availablePriceRange`;
- если пользователь выставил цену вне доступного диапазона, выдача может быть 0, но фильтры должны честно показать 0.

## 6. Backend: новая модель расчёта фасетов

Нужно доработать backend-логику, а не только UI.

### 6.1 Новая функция

Добавить или переработать функцию, например:

```ts
getCategoryFacets({
  categorySlug,
  activeFilters,
  locale,
}: {
  categorySlug: string
  activeFilters: ActiveFilters
  locale: 'uk' | 'ru'
})
```

Функция должна вернуть:

```ts
type FacetOption = {
  value: string
  label: string
  count: number
  selected: boolean
  disabled: boolean
}

type CategoryFacets = {
  total: number
  price: {
    absoluteMin: number
    absoluteMax: number
    availableMin: number
    availableMax: number
    selectedMin?: number
    selectedMax?: number
  }
  brands: FacetOption[]
  attributes: Record<string, FacetOption[]>
}
```

### 6.2 Где применять

Затрагиваемые места:

- `src/app/[locale]/(shop)/catalog/[slug]/page.tsx`
- `src/queries/categories.ts`
- `src/queries/products.ts`
- `src/components/catalog/catalog-filters.tsx`
- `src/components/catalog/price-range-filter.tsx`
- `src/components/catalog/mobile-filter-drawer.tsx`
- `src/components/catalog/catalog-toolbar.tsx`
- `src/lib/catalog-filter-url.ts`
- `src/lib/catalog-filter-config.ts`

### 6.3 Where builders

Нужно вынести построение Prisma where в reusable helper:

```ts
buildProductWhere({
  categorySlug,
  activeFilters,
  excludeFacetKey,
})
```

Примеры:

```ts
const resultWhere = buildProductWhere({
  categorySlug,
  activeFilters,
})

const brandFacetWhere = buildProductWhere({
  categorySlug,
  activeFilters,
  excludeFacetKey: 'brand',
})

const viscosityFacetWhere = buildProductWhere({
  categorySlug,
  activeFilters,
  excludeFacetKey: 'viscosity',
})
```

Важно:

- цена должна исключаться только при расчёте самого price range;
- при расчёте brands/attributes цена должна учитываться;
- внутри одной группы multi-select работает как OR;
- между группами работает AND.

## 7. Counts: правила

### 7.1 Brand counts

Brand count должен отвечать на вопрос:

```text
Сколько товаров будет, если выбрать этот бренд при текущих остальных фильтрах?
```

Если выбран price `500-1000`, бренд `PremiumBrand` с товарами от `5000` должен иметь count `0` и disabled.

### 7.2 Attribute counts

Attribute count должен отвечать на тот же вопрос:

```text
Сколько товаров будет, если выбрать это значение атрибута при текущих остальных фильтрах?
```

Пример:

```text
Цена: до 1000
Бренд: Castrol

Вязкость:
[ ] 5W-30 (3)
[ ] 5W-40 (0) disabled
```

### 7.3 Selected values

Selected values:

- не удалять из списка;
- показывать selected;
- если count 0, всё равно дать снять;
- count можно показывать 0, но UI должен подсказать, что комбинация пустая.

## 8. Performance

Нельзя делать N+1 запрос:

```text
один запрос на каждый бренд
один запрос на каждое значение каждого атрибута
```

Минимально допустимо для MVP:

- один ограниченный query по товарам категории с `take`;
- только `select` нужных полей: `id`, `price`, `stock`, `brand.slug`, `attributes`;
- `take` обязателен по AGENTS.md;
- если категория может быть большой, не грузить весь каталог.

Рекомендуемая production-реализация:

- агрегировать brand counts через SQL `GROUP BY`;
- агрегировать JSONB attributes через PostgreSQL JSONB functions;
- использовать параметризованные raw SQL только если Prisma не даёт нужной гибкости;
- сохранить/проверить GIN index `products_attributes_gin_idx`;
- не собирать SQL строками из пользовательского ввода.

Если используется raw SQL:

- только parameterized query;
- whitelist keys из `catalog-filter-config.ts`;
- никакого прямого подставления query params в SQL.

## 9. URL и pending state

Фильтры остаются URL-driven:

```text
/uk/catalog/motornye-masla?priceMin=500&priceMax=1000&brand=castrol&viscosity=5W-30
```

Требования:

- при изменении любого фильтра `page` сбрасывается в `1`;
- `sort` сохраняется;
- пустые значения удаляются из URL;
- неизвестные filter keys игнорируются или отбрасываются, если они не разрешены config-ом категории;
- во время перехода показывать subtle pending state в toolbar/sidebar;
- не использовать localStorage как источник истины.

## 10. Mobile drawer

На mobile логика должна быть идентичной desktop:

- counts такие же;
- disabled такие же;
- после изменения price или другого фильтра counts обновляются в drawer;
- sticky button должен показывать актуальное:

```text
Показати N товарів
```

Если `N = 0`, кнопка может быть disabled или показывать:

```text
Немає товарів
```

Рядом должна быть доступна очистка фильтров.

## 11. Микро-визуализация доступности внутри фильтров

Добавить небольшой, но полезный UX-слой: фильтр должен не только показывать counts, но и визуально подсказывать, где в диапазоне реально есть товары.

### 11.1 Пиксельная полоса на price/range фильтрах

Для цены и будущих числовых диапазонов, например мощность, ёмкость, ток, напряжение, добавить тонкую “пиксельную полосу” или мини-гистограмму над/под range slider.

Идея:

```text
500      1000      1500      2000      2500
|---------|---------|---------|---------|
  ▂ ▂▂ █ ███ ▂        ▂ ████ ▂
```

Требования:

- полоса строится по текущему набору товаров с учётом активных фильтров других групп;
- если в ценовом сегменте есть товары, сегмент подсвечивается;
- если товаров нет, сегмент остаётся пустым/приглушённым;
- selected price range можно показывать поверх полосы более ярким акцентом;
- не делать тяжёлую графику, достаточно 24-64 buckets;
- не использовать canvas без необходимости, можно обычными div/span;
- не ломать mobile drawer, на mobile полоса должна быть компактной.

Назначение:

- пользователь сразу видит, где есть реальные товары по цене;
- меньше случайных пустых диапазонов;
- легче понять, почему после выбора цены часть брендов/параметров стала disabled.

### 11.2 Пиксельная полоса для числовых технических фильтров

Для будущих range-фильтров по характеристикам использовать тот же принцип:

- ёмкость аккумулятора;
- мощность;
- ток;
- напряжение;
- сечение кабеля;
- количество полюсов, если будет удобно представить как шкалу.

Если фильтр не числовой, пиксельную полосу не делать.

### 11.3 Микро-иконки брендов

Для brand-фильтра можно добавить маленькие бренд-маркеры рядом с названием.

Требования:

- если есть официальный `brand.logo`, использовать маленькую иконку/лого в размере 16-20 px;
- если лого нет, генерировать аккуратный fallback: первая буква бренда или микро-знак на основе формы/цвета бренда;
- не использовать крупные цветные логотипы, которые ломают спокойный стиль Elektronom;
- иконка не должна заменять текст бренда, только помогать быстрее сканировать список;
- disabled brand должен приглушать и иконку тоже;
- selected brand может получать accent outline/checkmark.

Важно:

- не тянуть внешние лого с неизвестных доменов прямо в фильтры;
- использовать уже загруженные brand assets или безопасный fallback;
- не нарушать авторские права и не перерисовывать чужие логотипы вручную, если нет исходного asset.

## 11. Product cards не переделывать с нуля

Это ТЗ не про новый дизайн карточек.

Требование остаётся:

- использовать существующий `ProductCard` как базу;
- для категории использовать variant/mode `catalog`;
- не ломать стиль главной;
- изменения в карточке делать только если нужны для категории: стабильная высота, компактность, 3-5 характеристик, бейджи, нормальная сетка.

## 12. Acceptance criteria

Задача считается выполненной, если:

1. При изменении цены пересчитываются counts брендов и всех атрибутов.
2. Значения, которые дают 0 товаров при текущих фильтрах, disabled и визуально недоступны.
3. Disabled значения нельзя выбрать.
4. Выбранные значения с count 0 остаются видимыми и их можно снять.
5. Brand counts учитывают price, stock и выбранные attributes.
6. Attribute counts учитывают price, stock, brand и другие attributes, кроме своей группы.
7. Price range влияет на все остальные фасеты.
8. Multi-select внутри одной группы работает как OR.
9. Разные группы фильтров работают как AND.
10. Active chips корректно снимают фильтры и пересчитывают counts.
11. Desktop sidebar и mobile drawer показывают одинаковую логику.
12. URL остаётся источником состояния.
13. Не появляется N+1 запросов по каждому значению фильтра.
14. Все Prisma collection queries имеют `take`/`skip` и `select`.
15. Нет inline styles в новых/изменённых компонентах.
16. `npx tsc --noEmit` проходит.
17. `npm run lint` проходит.
18. `npm run build` проходит.
19. Price/range фильтр показывает компактную пиксельную полосу распределения товаров или явно оформленную заглушку, если данных для распределения пока нет.
20. Brand-фильтр поддерживает микро-иконки брендов через `brand.logo` или аккуратный fallback.

## 13. Обязательные тестовые сценарии

### Сценарий 1: цена отключает бренды

1. Открыть `/uk/catalog/motornye-masla`.
2. Установить price range, который оставляет только дешёвые товары.
3. Проверить brand list.
4. Бренды, у которых нет товаров в этом диапазоне, должны стать disabled/count 0.
5. Нельзя выбрать disabled brand.

### Сценарий 2: бренд пересчитывает характеристики

1. Выбрать бренд `Castrol`.
2. Проверить `viscosity`, `volume`, `type`.
3. Значения, которых нет у Castrol, disabled/count 0.

### Сценарий 3: характеристика пересчитывает бренды

1. Выбрать `viscosity=5W-30`.
2. Проверить brand counts.
3. Бренды без `5W-30` disabled/count 0.

### Сценарий 4: selected value count 0

1. Выбрать бренд.
2. Выставить цену, при которой товаров этого бренда нет.
3. Бренд остаётся selected.
4. Count показывает 0 или UI показывает конфликт.
5. Пользователь может снять бренд через checkbox или active chip.

### Сценарий 5: mobile drawer

1. Открыть категорию на 390px.
2. Открыть фильтры.
3. Изменить цену.
4. Проверить, что counts в drawer обновились.
5. Disabled значения недоступны.
6. Sticky button показывает актуальное количество товаров.

### Сценарий 6: пиксельная полоса цены

1. Открыть категорию с товарами в разных ценовых диапазонах.
2. Проверить, что на price slider видна компактная полоса распределения.
3. Выбрать бренд или атрибут.
4. Проверить, что полоса цены перестроилась под текущие остальные фильтры.
5. Выставить диапазон, где товаров нет.
6. Проверить, что выдача и counts честно показывают 0, а остальные фильтры стали disabled/muted.

### Сценарий 7: микро-иконки брендов

1. Открыть категорию с несколькими брендами.
2. Проверить, что brand list показывает маленькие иконки или fallback-маркеры.
3. Выбрать price range, при котором часть брендов недоступна.
4. Проверить, что disabled-состояние приглушает и текст, и иконку.
5. Выбрать бренд с иконкой и проверить selected state.

## 14. Короткое задание разработчику

Доработать фасетную логику категории: после выбора цены, бренда, наличия или любого атрибута остальные фильтры должны пересчитывать counts относительно текущей выдачи. Значения, которые дают 0 товаров, не должны выглядеть доступными: показывать disabled/muted, но выбранные значения не скрывать, чтобы их можно было снять. Реализовать это на backend уровне через общий where-builder и корректный расчёт фасетов, а не только через CSS. Desktop sidebar и mobile drawer должны использовать одну и ту же facet-модель. Existing `ProductCard` не переделывать с нуля.

Дополнительно добавить микро-визуализацию: на price/range фильтрах показывать пиксельную полосу распределения товаров, а в brand-фильтре поддержать маленькие бренд-иконки или fallback-маркеры. Это должно помогать пользователю понять, где в диапазоне реально есть товары, а какие бренды/параметры уже недоступны при текущих условиях.
